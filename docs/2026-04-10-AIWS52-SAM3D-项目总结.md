## 二、数据集整理：从无结构到可运行

### 2.1 原始问题

AIWS5.2 原始数据最初是以“图片、深度、标注集中堆放”的方式存在，没有形成后续算法流程需要的结构化层次。这种组织方式带来几个明显问题：

- 难以按工件类别组织样本
- 难以区分 `V1 / V2 / NEW` 三类子集
- 难以保留训练集/验证集划分
- 多实例图像不方便做实例级处理
- 后续做批量 3D 重建时不利于自动化

### 2.2 第一阶段结果：`aiws5.2-usable`

第一阶段构建了一个**非破坏性符号链接视图** `aiws5.2-usable/`，其核心思想是：

- 以 `isat_annotations/` 为标注真值来源
- 不复制原始大文件，只通过 symlink 组织目录
- 按 `V1 / V2 / NEW` 分子集
- 每个子集下再按工件类别分组

这一版本主要用于快速建立一个“干净可用”的单实例视图，且为后续单实例 mask 生成提供基础。

该视图的统计结果为：

- 主视图图像数：**1418**
- 多实例图像：**23**
- 多标签图像：**0**
- 未标注图像：**1**

但是，这个版本有一个局限：

- 多实例图像会被整体移到 `misc/multi_instance/`
- 因此不适合作为最终的“按实例逐个跑 SAM3D”的正式输入

### 2.3 第二阶段结果：`aiws5.2-usable-split`

为了解决上面的问题，随后构建了第二版结构化视图 `aiws5.2-usable-split/`。这一版的设计更贴近最终实验要求：

- `train / val` 成员归属来自 `train.json` 和 `val.json`
- 标注内容仍然以 `isat_annotations/` 为准
- 保留 `V1 / V2 / NEW` 的子集信息
- 保留多实例图像，以支持后续实例级拆分处理

它的意义在于：

- 避免 COCO 导出里的 dropped-instance 问题
- 又不会丢失训练/验证划分
- 为后续按实例批量 SAM3D 推理提供了正确的数据视图

这一版的统计结果为：

- 图像总数：**1441**
- 实例总数：**1475**
- 未标注图像：**1**
- `missing_split / missing_image / missing_depth` 均为 **0**

这组数字非常关键，因为它明确说明：

- 后续 SAM3D 运行不是 1441 次，而是 **1475 次实例级任务**

### 2.4 materialized 版本

为了在服务器上稳定运行，而不是依赖本地符号链接视图，又进一步准备了 materialized 版本：

- `aiws5.2-usable-materialized/`
- `aiws5.2-usable-split-materialized/`
- `aiws5.2-usable-split-materialized.zip`

最终服务器实际使用的数据目录为：

- `/ssd1/rxl/zhankaiming/aiws5.2-usable-split-materialized`

## 三、SAM3D 重建环境恢复：本地克隆，再上传服务器

### 3.1 为什么不能直接在服务器上重新拉仓库

`RXL` 服务器位于中国网络环境，对 GitHub 和 Hugging Face 的访问不稳定。直接在服务器上执行 `git clone` 时，出现了：

- GitHub HTTPS 连接超时
- 无法可靠地从服务器直接获取完整仓库与依赖

因此采取了替代方案：

1. 在本地机器上先克隆官方 SAM3D 仓库
2. 在本地确认仓库完整可用
3. 再通过 SSH/同步方式上传到服务器

恢复后的仓库路径为：

- `/ssd1/rxl/zhankaiming/sam-3d-objects`

仓库对应 commit：

- `81a82373a3a7f4cbb00bd5b32aaf6b4d0f659ddd`

### 3.2 为什么仅有仓库还不够

重新拉好仓库后，服务器端仍然不能直接运行，原因是缺少多个运行时资产：

- `checkpoints/hf/pipeline.yaml`
- SAM3D 所需 checkpoint
- MoGe 本地模型文件
- DINOv2 的本地缓存和 checkpoint

随后完成了以下恢复：

- 从旧备份中恢复约 12 GB 的 checkpoint 资源
- 将 MoGe 权重放到服务器本地路径并修改配置引用
- 把 DINOv2 的 torch hub cache 与 checkpoint 补到服务器上

这些修复完成后，`python demo.py` 首次在服务器上完整跑通。

## 四、`flash_attn` 调试：A6000 不是 A100/H100/H200

### 4.1 第一个问题：`flash_attn` 根本导不进来

最早的 `flash_attn` 问题不是 CUDA 算力不足，而是**预编译 wheel 与服务器 glibc 不兼容**。也就是说：

- 不是 A6000 不能用 `flash_attn`
- 而是服务器上的环境加载不了现成 wheel

因此解决方式不是继续换 wheel，而是：

- 在服务器本地做源码编译
- 针对 Ampere 路径编译
- 最终让 `flash_attn 2.8.3` 在 `sam3d-objects` 环境里成功 import

### 4.2 第二个问题：即便能 import，SAM3D 仍然默认走 `sdpa`

导入成功后，端到端运行仍然没有自动启用 `flash_attn`。进一步检查发现：

- SAM3D 仓库内部有 GPU 白名单逻辑
- 默认只对 `A100 / H100 / H200` 等工业级卡自动选择 `flash_attn`
- RTX A6000 不在自动白名单中

这意味着：

- **安装成功** 不等于 **运行时使用成功**

### 4.3 最终解决

没有继续大改主仓库逻辑，而是在运行时显式覆盖：

- `ATTN_BACKEND=flash_attn`
- `SPARSE_ATTN_BACKEND=flash_attn`

验证后确认：

- A6000 上确实能正常跑 `flash_attn`
- dense 和 sparse attention 都实际切到了 `flash_attn`

### 4.4 辅助运行脚本

为了让 demo 和后续重复运行更安全，在服务器上保留了：

- `/ssd1/rxl/zhankaiming/run_sam3d_demo.sh`
- `/ssd1/rxl/zhankaiming/SAM3D_RUNTIME.md`

其中脚本支持：

- `SAM3D_DRY_RUN=1`
- 默认拒绝覆盖已有输出
- 默认导出 `flash_attn` 相关环境变量

此外还修复了 `conda activate` 和 `set -u` 的兼容性问题。

## 五、SAM3D 批量脚本与输出格式修正

### 5.1 批处理脚本建立

为了对结构化后的 AIWS5.2 数据集做实例级批量重建，新增了：

- `scripts/run_sam3d_aiws52_batch.py`

这个脚本支持：

- 遍历整个 `aiws5.2-usable-split-materialized`
- 每个实例单独输出
- 记录 `manifest.csv / results.jsonl / summary.json / meta.json`
- 支持 `--resume`
- 记录实例级运行指标
- 支持多卡分片运行

### 5.2 离线环境修复：DINO 加载重定向到本地 cache

批处理首次 smoke test 暴露出一个新问题：

- 即使 DINOv2 cache 已经存在
- `torch.hub` 在某些路径上仍然会尝试重新访问 GitHub

这在中国服务器环境下是不可靠的。

最终在 batch runner 内部增加了一个小型补丁：

- 如果请求的是 `facebookresearch/dinov2`
- 且 `source=github`
- 就自动重定向到本地缓存目录

这样避免了修改主仓库，同时让 batch runner 能在弱联网环境中稳定运行。

### 5.3 第一轮错误输出：保存成了 gaussian-splat

最初版本的 batch runner 保存的是：

- `output["gs"] -> splat.ply`

但这不是本次项目真正想要的最终产物。

Leonardo 指出后，进一步检查 pipeline 发现：

- `gs` 是 gaussian 表示
- `glb` 才是后处理后的 mesh 对象

因此批处理脚本随后改为输出：

- `mesh.glb`

### 5.4 为 Cadrille 兼容再增加 `mesh.stl`

后来又进一步明确：

- Cadrille 后续流程更容易处理 `.stl`

因此最终版本的 batch runner 会同时输出：

- `mesh.glb`
- `mesh.stl`

这使得：

- `glb` 可用于通用 mesh 交换和可视化
- `stl` 更方便后续工艺/几何流水线使用

## 六、当前正式运行状态

### 6.1 运行组织方式

当前正式运行采用了 **4 卡分片并行**：

- 4 张 RTX A6000
- 4 个 worker
- 每个 worker 负责一个 shard
- 每个实例仍然保留独立 runtime 统计

这里的 shard 并不是特殊算法，而只是把 1475 个实例按 `global_index % 4` 拆成 4 个不重叠子集，以便并行处理：

- shard 0
- shard 1
- shard 2
- shard 3

这保证了：

- 不会重复处理
- 不会漏处理
- 每个实例仍然可以独立追踪运行时间、显存和输出位置

### 6.2 当前全量运行目录

- 运行根目录：`/ssd1/rxl/zhankaiming/outputs/sam3d-aiws52-full-mesh-stl-20260410-161655/`

每个 shard 下都有自己的：

- `run.log`
- `summary.json`
- `results.jsonl`
- `manifest.csv`

### 6.4 当前失败模式

截至当前，已经记录到 **5 个失败实例**，主要模式是：

- `BoundingBoxError: Bounding box dimensions must be at least 2x2.`
- 少量空输入相关错误，例如：
  - `RuntimeError: max(): Expected reduction dim to be specified for input.numel() == 0.`

目前看，这些更像是**个别标注或极端实例的边界问题**，而不是系统性环境故障。重要的是：

- 单个实例失败不会中断整个全量运行
- runner 会继续处理剩余样本
