## 3. AIWS5.2 数据集重组

### 3.1 原始问题

当天早些时候，AIWS5.2 原始数据处于“文件集中堆放”的状态，图像、深度和标注没有以训练/验证、子集、工件类别的方式组织。这个状态有几个直接问题：

- 不方便按工件类别抽取样本
- 不方便按深度类型区分 `V1 / V2 / NEW`
- 不方便后续批量推理
- 不方便处理多实例样本
- 容易在训练/验证划分与真实标注之间出现错配

因此，第一阶段的目标不是直接复制数据，而是先建立**非破坏性、可追溯、可复用**的数据视图。

### 3.2 第一版：构建“可用视图” `aiws5.2-usable`

对应脚本：`scripts/build_aiws52_usable_view.py`

设计原则：

- **标注真值以 `isat_annotations/` 为准**
- 不复制原始大文件，使用**符号链接视图**组织数据
- 按子集组织：
  - `V1`，无深度
  - `V2`，深度为 `.png`
  - `NEW`，深度为 `.exr`
- 每个子集下按工件类别组织：
  - `cover_plate`
  - `square_tube`
  - `h_beam`
  - `channel_steel`
  - `bellmouth`

第一版视图的核心策略是：

- 如果一张图只有 1 个实例，并且标签单一，则进入主目录
- 如果一张图含多个实例，则进入 `misc/multi_instance/`
- 如果一张图含多个类别，则进入 `misc/multi_label/`
- 没有标注但有图像的样本进入 `misc/unannotated_images/`

这个版本的优点是干净，适合“单实例”实验，但也带来了一个后续问题：

- **多实例图像被整体移出主目录**，这对于后续“按实例逐个跑 SAM3D”的方案并不合适

### 3.2.2 单实例掩码生成

对应脚本：`scripts/generate_aiws52_instance_masks.py`

用途：

- 从 `isat_annotations/` 中读取单实例 polygon 标注
- 生成与图像同尺寸的二值 mask PNG
- 输出 `metadata/masks.csv` 作为 mask 清单

这一步为后续单实例实验准备了标准化掩码，但由于主视图本身排除了多实例图像，因此不适合作为最终的全量 SAM3D 批处理输入。

### 3.3 第二版：构建 split-aware 视图 `aiws5.2-usable-split`

对应脚本：`scripts/build_aiws52_split_view.py`

在第一版完成后，我们重新梳理目标，发现最终需求并不是“只保留干净的单实例样本”，而是：

1. 保留 `train/val` 划分
2. 保留真实标注
3. 对多实例图像中的**每个实例**都允许后续单独重建
4. 避免 COCO 导出过程里出现“丢实例”问题

因此，第二版视图改为：

- `train/` 和 `val/` 的成员归属由 `train.json` / `val.json` 决定
- 标注内容仍以 `isat_annotations/` 为准
- 每张图仍按 `V1 / V2 / NEW` 与工件类别组织
- **不再因为多实例而直接把图像排除出主结构**
- 一个图像可以在统计中对应多个 object 实例

该视图的 README 明确指出：

- 这是 split-aware 的非破坏性符号链接视图
- 它避免了 COCO 导出阶段的 dropped-instance 问题
- 同时保留了 train/val 的成员关系

## 5. `flash_attn` 与 RTX A6000 调试过程

### 5.1 初始问题：`flash_attn` 导入失败

在 `sam3d-objects` 环境中，最初的 `flash_attn` 问题不是 CUDA 本身不支持，而是二进制兼容问题：

- 预编译 wheel 依赖 `GLIBC_2.32`
- 服务器运行环境无法满足该要求

因此，直接安装 wheel 并不能在 `RXL` 上工作。

### 5.2 根因一：需要真正的本地源码编译

我们确认真实问题是：

- 不是 CUDA capability 不够
- 不是 A6000 不能跑 attention kernel
- 而是预编译 wheel 与服务器的 glibc 版本不兼容

因此修复策略改为：

- 在服务器本机进行 `flash_attn` 源码编译
- 明确限制为 Ampere 相关代码路径
- 针对 RTX A6000 的 `sm86` 场景做兼容性处理

这一步最终成功，`flash_attn 2.8.3` 可以在 `sam3d-objects` 环境中正常导入。

### 5.3 根因二：即便导入成功，SAM3D 默认仍不会在 A6000 上选中 `flash_attn`

接下来的问题更隐蔽：

- `flash_attn` 已经能 import
- 但 SAM3D 端到端跑起来时仍然选择 `sdpa`

进一步检查发现，这是仓库内部逻辑导致的，而不是安装失败：

- `sam3d_objects/pipeline/inference_pipeline.py`
- 只会在 `A100 / H100 / H200` 等白名单 GPU 上自动启用 `flash_attn`
- 对 RTX A6000 不会自动切换

这意味着：

- **导入成功 ≠ 运行时使用成功**

### 5.4 解决方案：显式覆盖 attention backend

最终方案不是继续大改主仓库，而是通过运行时环境变量强制启用：

- `ATTN_BACKEND=flash_attn`
- `SPARSE_ATTN_BACKEND=flash_attn`

验证结果表明：

- A6000 上可以稳定运行 `flash_attn`
- dense attention 和 sparse attention 的日志中都出现了 `flash_attn`

### 5.5 运行辅助脚本修复

为了让重复运行更安全，服务器上增加了：

- `/ssd1/rxl/zhankaiming/run_sam3d_demo.sh`
- `/ssd1/rxl/zhankaiming/SAM3D_RUNTIME.md`

脚本能力包括：

- `SAM3D_DRY_RUN=1` 用于安全检查
- 默认拒绝覆盖已有输出，除非显式设置 `SAM3D_OVERWRITE=1`
- 默认导出 `ATTN_BACKEND=flash_attn`
- 默认导出 `SPARSE_ATTN_BACKEND=flash_attn`

另外还修复了一个 shell 层问题：

- 原脚本使用 `set -u`
- 在 `conda activate` 过程中触发了 `activate-binutils_linux-64.sh` 对 `ADDR2LINE` 的引用错误

最终修复方式为：

- 在 `source conda.sh` 与 `conda activate` 周围临时关闭 `nounset`
- 激活完成后再恢复严格模式

修复后，SAM3D demo 在 A6000 上成功运行。

## 7. 批处理脚本的指标增强与 4 卡并行

### 7.1 指标增强

为了支持后续分析与实验报告，批处理脚本在当天被增强为记录以下指标：

- `model_init_sec`：模型初始化时间
- `duration_sec`：单实例端到端处理时间
- `instances_per_hour`
- `sec_per_megapixel`
- `image_pixels`
- `mask_pixels`
- `mask_fraction`
- `peak_memory_allocated_mb`
- `peak_memory_reserved_mb`
- `gpu_name`
- `cuda_visible_devices`
- `num_shards`
- `shard_index`

这里需要强调：

- `duration_sec` 是**单实例真实处理时长**
- 不包括该 worker 的一次性模型冷启动
- 冷启动被单独记录为 `model_init_sec`

因此，后续既可以分析单实例吞吐，也可以单独分析冷启动开销。

### 7.2 4 卡分片（sharding）

服务器确认可用 GPU 为 4 张 RTX A6000，因此没有继续采用单进程串行策略，而是把任务集拆成 4 个不重叠分片：

- shard 0：`global_index % 4 == 0`
- shard 1：`global_index % 4 == 1`
- shard 2：`global_index % 4 == 2`
- shard 3：`global_index % 4 == 3`

这样做的效果是：

- 没有重复实例
- 没有漏掉实例
- 每个实例仍然保留独立的 runtime 统计
- 可以做到 1 个进程绑定 1 张 GPU

这也是后续全量运行的正式组织方式。

## 8. 输出格式修正：从 splat 到 mesh，再到 GLB + STL

### 8.1 第一个错误：批处理保存成了 gaussian-splat

在一次 smoke test 后，Leonardo 指出一个关键问题：

- 目标产物不是 `gaussian-splat`
- 而是 **mesh**

检查 SAM3D pipeline 后发现：

- `output["gs"]` 是 gaussian 模型对象，支持 `save_ply`
- `output["mesh"]` 是原始 mesh 提取结果
- `output["glb"]` 是经过后处理后的 `trimesh.Trimesh`，可以直接 `.export(...)`

也就是说，批处理此前保存的是**错误分支**。

### 8.2 第二步修正：改为保存 `mesh.glb`

随后批处理改为：

- 不再输出 `splat.ply`
- 改为导出 `mesh.glb`
- 在 `meta.json` 中记录：
  - `mesh_path`
  - `mesh_size_bytes`
  - `artifact_format`

对应 smoke test：

- 目录：`/ssd1/rxl/zhankaiming/outputs/sam3d-aiws52-smoke-mesh-20260410-1552/`
- 样例：`train/NEW/cover_plate/NEW-G140-11__obj01`
- `mesh.glb` 大小约 **8.7 MB**

### 8.3 第三步修正：为 Cadrille 增加 `mesh.stl`

之后 Leonardo 进一步指出：

- 后续 Cadrille pipeline 更方便使用 `.stl`

因此批处理脚本再次扩展为双产物导出：

- `mesh.glb`
- `mesh.stl`

对应 smoke test：

- 目录：`/ssd1/rxl/zhankaiming/outputs/sam3d-aiws52-smoke-mesh-stl-20260410-1613/`
- `mesh.glb`：约 **8.7 MB**
- `mesh.stl`：约 **22 MB**

此时 `meta.json` 也同步记录：

- `mesh_path`
- `stl_path`
- `artifact_formats`
- `mesh_size_bytes`
- `stl_size_bytes`

### 8.3.1 双格式输出的存储评估

基于 smoke test 的实际大小估算：

- 单实例约：`8.7 MB (GLB) + 22 MB (STL)`
- 1475 实例总计约：**46.9 GB**

而服务器 `/ssd1` 当前剩余空间约：

- **759 GB**

因此当前双格式全量输出在存储上是安全的，不构成阻塞。
