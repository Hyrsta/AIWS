## 3. AIWS5.2 正式数据集方案

### 3.1 目标

本项目最终采用的正式数据集目标非常明确：

- 使用结构清晰、可直接批处理的目录布局
- 保留 `V1 / V2 / NEW` 子集信息
- 保留工件类别目录
- 每个正式任务对应一个明确对象
- 避免多实例图像给重建结果与文档叙述带来歧义

因此，正式运行使用的是**清洗后的单实例数据集**：

- `aiws5.2-usable-materialized`

### 3.2 数据组织方式

该数据集是一个面向工程使用的 materialized 版本，按如下层级组织：

- `V1/`
- `V2/`
- `NEW/`

每个子集下再按工件类别组织，例如：

- `cover_plate`
- `square_tube`
- `h_beam`
- `channel_steel`
- `bellmouth`

每个工件目录中包含：

- `images/`
- `annotations/`
- `depth_png/` 或 `depth_exr/`（若该子集有深度）

### 3.3 数据原则

本次正式实验的数据组织遵循以下原则：

- 标注真值来源为 `isat_annotations/`
- 正式运行只使用清洗后的主视图
- 多实例图像不进入正式运行集合
- 未标注图像不进入正式运行集合
- 后续文档、实验统计、方法描述，统一以该清洗版数据集为准

## 4. SAM3D 接收的输入与批处理方式

### 4.1 单个任务的输入

对于正式运行中的每个样本，SAM3D 接收的核心输入是：

1. RGB 图像
2. 由标注 polygon 栅格化得到的二值 mask
3. 随机种子 `seed`

也就是说，本项目不是先把全部 mask 离线保存好再作为唯一输入，而是由 batch runner 在运行时完成：

- 读取 annotation JSON
- 提取目标对象的 polygon
- 栅格化为二值 mask
- 与 RGB 图像一起送入 SAM3D

### 4.2 当前批处理脚本做了什么

对应脚本：`scripts/run_sam3d_aiws52_batch.py`

当前脚本流程为：

1. 遍历 `aiws5.2-usable-materialized`
2. 按样本生成任务列表
3. 读取对应 annotation JSON
4. 将 polygon 转成二值 mask
5. 调用 SAM3D `Inference(image, mask, seed)`
6. 导出 `mesh.glb` 与 `mesh.stl`
7. 记录 `manifest.csv`、`results.jsonl`、`summary.json`、`meta.json`

### 4.3 当前输出格式

正式运行输出双格式：

- `mesh.glb`
- `mesh.stl`

这样既满足通用 mesh 可视化需求，也兼容后续 Cadrille 流水线的使用方式。

## 6. `flash_attn` 与 RTX A6000 调试

### 6.1 问题一：预编译 wheel 不兼容

最初的 `flash_attn` 问题不是 CUDA 算力不足，而是二进制兼容问题：

- 预编译 wheel 依赖 `GLIBC_2.32`
- 服务器运行环境不能直接满足该要求

因此最终采用的方案不是换 wheel，而是：

- 在服务器本机进行源码编译
- 面向 Ampere 路径构建
- 在 `sam3d-objects` 环境中验证导入成功

### 6.2 问题二：A6000 不会被仓库默认切到 `flash_attn`

即使 `flash_attn` 可以 import，SAM3D 默认也不会在 RTX A6000 上自动选择它。仓库内部白名单主要面向：

- `A100`
- `H100`
- `H200`

因此最终通过环境变量显式覆盖：

- `ATTN_BACKEND=flash_attn`
- `SPARSE_ATTN_BACKEND=flash_attn`

### 6.3 当前结果

在 `RXL` 的 4 张 RTX A6000 上，当前正式运行已经确认：

- dense attention 使用 `flash_attn`
- sparse attention 使用 `flash_attn`
- 运行日志中可见对应 backend 信息

## 8. 正式运行组织方式

### 8.1 运行方式

当前正式实验采用 4 卡并行：

- 4 张 RTX A6000
- 4 个 worker
- 4 个 shard

分片原则为：

- `global_index % 4 == 0`
- `global_index % 4 == 1`
- `global_index % 4 == 2`
- `global_index % 4 == 3`

这保证了：

- 不重复处理
- 不漏处理
- 每个实例仍保留独立 runtime 统计
